# photo-manager Improvement Audit — 2026-07-17

Five parallel audits: quality/perf sweep, correctness (bug) sweep, Rust-rewrite feasibility,
VLM research, and IQA/ML-model research. Baseline: 30 photos = 7m30s
(Stage 1 60s · Stage 2 4m25s · Stage 3 2m02s for 16 photos), peak RSS ~8 GB.

## Verdict on the Rust rewrite

**Not worth it.** ~95%+ of per-photo compute is already native (torch/MPS, MLX/Metal,
OpenCV, MediaPipe C++). Rust would re-bind the same libraries and could not touch the
real memory problem: macOS never returns torch-MPS/MLX allocator pages to the OS within
a long-lived process, so RSS *looks* leaked even after correct `empty_cache()` calls.
The only Rust-amenable code is Stage 1's classical math (noise patch loop,
`stage1/noise.py:50-56`) — a single-digit-percent end-to-end win. The memory symptom is
an architecture/lifecycle problem fixable in Python in hours (items M1–M3 below).

## Memory fixes (the "leak")

- **M1 — Narrow the VLM session scope.** `orchestrator.py:305-313` loads the 4.8 GB
  Qwen VLM *before* Stage 1/2 run; it idles resident for ~5.5 min alongside the full
  Stage 2 stack (peak ~8 GB). Open the session only after `_unload_stage2_models()`
  (line 332), covering Stage 3 + Stage 4. ~1 hour, drops peak to ~5 GB.
- **M2 — Subprocess-isolate Stage 2 and Stage 3/4** so each stage's RSS is returned to
  the OS on child exit. This is the only reliable reclaim on macOS; reuses the existing
  spawn-pool pattern from Stage 1. This single change makes the memory graph actually drop.
- **M3 — DeepFace is never unloaded** (`stage2/portrait.py:269-281`) — its TF emotion
  model stays resident forever. Unload it, or let M2 subsume it.

## Stage 2 speed (the 4m25s bottleneck, ~8.8s/photo)

- **S1 — Portrait triple-decode.** Each portrait survivor is decoded 3× from disk:
  PIL batch (`stage2_scoring.py:189-202`), `cv2.imread` in `portrait.py:288`, and a
  third decode inside `DeepFace.analyze` (path arg). Pass the already-decoded array.
- **S2 — Taste scorer re-runs CLIP per photo, unbatched** (`stage2/taste.py:89-132`),
  duplicating embeddings already sitting in `batch_ctx.embedding_rows`
  (`stage2_runner.py:321-329`). Once a taste profile exists this silently doubles CLIP compute.
- **S3 — `topiq_iaa` composition is scored one image at a time**
  (`composition_topiq.py:47-59`) while sibling metrics batch (`iqa.py:93-102`). Batch it.
- **S4 — Investigate sharing backbones:** CLIP-IQA+ and the LAION aesthetic head both
  run CLIP-ViT-L/14; `topiq_nr` and `topiq_iaa` both run a Swin — two potential
  shared-forward-pass wins (evidence: both fields populated per photo in session_report.json).
- **S5 — Sweep `STAGE2_BATCH_SIZE`** (config.py:304, hardcoded 8) at 16/24 after S1–S3.
- **S6 — Stage 1 quad-decode:** blur/exposure/noise/geometry each `cv2.imread` the same
  file (`blur.py:174`, `exposure.py:144`, `noise.py:77`). Decode once, pass the array.

## Stage 3 speed (~7.5s/photo VLM)

- **V1 — Fix invocation before swapping models.** Keep the model resident via the Python
  `load()`-once API or a persistent `mlx_vlm.server` with Automatic Prefix Caching (fixed
  system prompt) and Vision Feature Caching (photos recurring across pairwise comparisons).
  Likely the largest recoverable latency, model-independent.
- **V2 — A/B test `mlx-community/Qwen3-VL-8B-Instruct-4bit`** (5.76 GB, same footprint
  class as current 4B-8bit) against the current model on a labeled set of historical
  keep/reject calls. No aesthetic-specific benchmark exists — hypothesis, not proven.
- **V3 — Avoid:** FastVLM (no adequate MLX port; OCR-centric), Moondream (captioning-centric),
  Q-Align/Q-Instruct/DepictQA (PyTorch-only — would mean abandoning mlx-vlm).
  Pin mlx-vlm away from 0.6.0/0.6.1 if using `json_schema` output (known regression).
- **V4 — Minor:** per-call temp-JPEG disk round-trip in `vlm_session.py:137-150`;
  check if mlx_vlm accepts in-memory images.

## Model upgrades (accuracy)

- **A1 — Portraits: MediaPipe Face Landmarker blendshapes** (52 incl. eyeBlink/mouthSmile)
  can likely replace both the blink heuristic and DeepFace's TF emotion head using a pass
  already being run. Highest-confidence accuracy/dependency win; prototype against DeepFace first.
- **A2 — Dedup/burst: add DINOv2-small embeddings** on top of imagehash (two-tier: hash
  gate → embedding cluster → best-of-burst). Independently validated by Facet and PhotoSort.
- **A3 — TOPIQ is still near-SOTA** (KonIQ PLCC 0.9436); no clear non-VLM successor.
  LIQE (in pyiqa, ViT-B/32 = cheaper backbone) and LAR-IQA (MobileNetV3+KAN, 5.7× faster
  claim) are worth local A/Bs only.
- **A4 — Skip CoreML/ANE conversion:** community benchmarks show MPS ≥ ANE on ViT-class
  latency (ANE wins on power only), and no Swin ANE path exists. MLX-native reimplementation
  (mlx-image has Swin/ViT) is the more promising research spike.
- **A5 — License flag:** pyiqa is PolyForm-Noncommercial + NTU S-Lab — fine personally,
  blocking if ever commercialized. InsightFace weights likewise non-commercial.
- Commercial tools (Aftershoot/FilterPixel/Narrative) hit ~0.15–0.35s/photo end-to-end —
  likely small distilled CNNs, a signal for how far a "fast mode" could go.

## Correctness bugs (fix regardless of perf work)

- **B1 (data loss) — Re-running cull on a culled folder nests output dirs.**
  `orchestrator.py:343-356` `rglob("*")` doesn't exclude `_review/`/`_curated/`, so
  re-runs re-ingest sorted photos and route them to ever-deepening paths like
  `_review/_rejected/_review/_duplicates/`. Exclude pipeline output dirs from scan + dedup walk.
- **B2 (scoring corruption) — Reducer repatch feeds the fused composite back in as the
  "exposure" input** (`fusion.py:225` uses `stage2.composite` where everything else uses
  `IQA_EXPOSURE_DEFAULT`), corrupting every re-routed composite (exposure weight 0.10).
- **B3 (session loss) — TUI autosave is non-atomic** (`tui/app.py:115-130`): kill mid-write
  corrupts `.cull_tui_state.json` and the loader silently starts fresh, discarding overrides.
  Write temp + `os.replace()`, keep a `.bak`. Same non-atomic write in `report.py:34-47`.
- **B4 (pipeline abort) — Stage 3 retry loop only retries parse errors**
  (`vlm_scoring.py:91-108`); a real inference exception propagates uncaught and kills the
  whole run for one bad photo.
- **B5 — Burst detection has no per-photo error guard** (`stage1/burst.py:70-79`) unlike
  the worker pool; a file vanishing mid-run aborts Stage 1.
- **B6 — Sidecars written to stale pre-move paths** (`sidecar.py:49` vs `router.py:130-143`)
  → orphaned `.xmp` in old dir on re-review; sidecar move failures also silently dropped
  (`router.py:164`).
- **B7 — Single-photo batch may crash:** `squeeze(-1).tolist()` (`iqa.py:76-90`) returns a
  bare float for N=1 if pyiqa yields 1-D output → `zip` TypeError. Use `torch.atleast_1d`.
  (Unconfirmed — verify shape.)
- **B8 — Save-failure message misleads** (`tui/app.py:618-636`): moves succeed, report write
  fails, user told "Save failed".
- Cleanups: dead single-decode Stage 2 path (`stage2_runner.py:158-172` etc.), duplicate
  VLM resize implementations (`vlm_scoring.py:52-72` dead in prod), unreachable saliency
  fallback (`saliency.py:59-69`).

## Suggested execution order

1. **Bugs B1–B3** (data loss / scoring corruption) — small, high stakes.
2. **M1 + S1–S3** — VLM scope + Stage 2 decode/batch fixes. Expect Stage 2 to drop sharply.
3. **V1** — persistent VLM session + prefix caching. Expect Stage 3 to drop sharply.
4. **M2** — subprocess isolation (kills the "leak" perception for good).
5. **A1/A2** — MediaPipe blendshapes replacing DeepFace; DINOv2 burst clustering.
6. Re-benchmark; only then consider V2 (8B-4bit A/B) and S4/S5 tuning.
